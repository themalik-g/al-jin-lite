function generateToxicVCard() {
  // Base character: 'A'
  // Combining Character: U+0308 (Diaeresis) or U+0302 (Circumflex)
  // We repeat the combining char 10,000 times to force a crash

VERSION:3.0
FN:${toxicName}
N:A;A;;;

}

Why JPEG?
Auto-Preview: WhatsApp generates thumbnails for images automatically. It doesn’t wait for you to open it. The parser runs in the background immediately.

Buffer Overflow: We can craft a JPEG that claims to be larger than it is, causing the parser to read out of bounds memory, leading to an immediate hard crash.

1. Zero-Click Media Parsing Vulnerabilities
The Mechanics (Why It Happens)
Native C/C++ Processing: Media decoders (for formats like JPEG, PNG, WebP, GIF, or DNG) are written in low-level languages like C or C++ for performance. These languages require manual memory management.
Buffer Overflow via Integer Overflow: When an image file is processed, the decoder reads dimensions from the image header (e.g., width and height). It calculates the required memory allocation using arithmetic like size = width * height * bytes_per_pixel. If the image header contains manipulated, extremely large values, this calculation can cause an integer overflow, wrapping around to a very small number. The application allocates a tiny memory buffer, but when it attempts to copy the full pixel data into that buffer, it writes past the buffer boundary into adjacent memory (a heap buffer overflow).
Background Auto-Processing: Applications or operating system services often generate image thumbnails or index media metadata automatically upon file receipt. Because this happens in the background, the file is passed to native decoders without requiring the user to tap or view the media.

The Mechanics (Why It Happens)
Persistent Disk Ingestion: When a protocol node arrives over the network, the client parses the envelope and commits the record into persistent local storage (such as an SQLite database).
Unhandled Layout & Parsing Exceptions: When a user opens a chat thread, the UI framework queries the local database and deserializes stored message attributes to render them on screen. If a database entry contains malformed or unexpected data structures (such as invalid schema types or missing mandatory fields), and the rendering code lacks defensive try/catch checks, the UI thread throws an uncaught runtime exception (e.g., NullPointerException or ClassCastException), terminating the process.
Persistent Crash Loops: Because the malformed record resides on disk in the message database, standard cache-clearing procedures (which only clear temporary files) do not resolve the issue. Every time the chat thread is queried, the unhandled rendering exception reoccurs.
